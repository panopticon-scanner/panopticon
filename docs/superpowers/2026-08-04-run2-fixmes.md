# Run-2 FIXMEs — defects in panopticon's own orchestration

These did not come from a reviewer panel. They are defects in how the scan
itself ran, observed by the orchestrator while running it. They belong in the
issue tracker alongside the findings — filing only what the panels said would
be a quieter, less honest report than the run deserves.

Each is written to be filed as one issue. Labels assume the catalog in
`.github/labels.yml`.

---

## FIXME-1 — Scout prompt omits a schema-required field
`self-scan`, `severity:medium`, `evidence:tool-confirmed`, `panel:architecture`

The hand-rolled scout assignment block lists the return fields as
`(group, files, surfaces, panels, lenses, depth, risk, tools, has_deps)`.
`reference/scope-profile-schema.json` requires
`['group','languages','surfaces','risk','lenses','panels']` — **`languages` is
required and is not in the list.** Six of ten scouts in run 2 omitted it; the
orchestrator backfilled by hand. Run 1's prompts carried the identical defect,
undetected.

Nothing validates a ScopeProfile against its own schema at any point in the
pipeline, so a scout can return an invalid profile and the run continues.

**Fix:** implement the pending `--render-scout` so scout prompts are generated
from one source of truth, and validate returned profiles against
`scope-profile-schema.json` (advisory, per the tolerant-by-design rule).

**External corroboration (2026-08-04, BursarBuddy calibration run), and it is
worse at the tier we ship.** An independent operator ran the scout on `haiku` —
the tier `EMIT_MODEL_POLICY` assigns it (`dispatch.py`) — and **both** scouts,
independently, on different groups, returned free-form JSON containing **none**
of the six required ScopeProfile fields. The same prompts on `sonnet`, with the
field names listed inline, worked first try for both. Our run-2 observation
(6 of 10 scouts dropping one field) understated this: at the assigned tier the
scout contract is not partially met, it is not met at all.

That points the fix at the prompt, not just the tooling: `scout.md` currently
names `reference/scope-profile-schema.json` by path and expects the agent to
open and conform to it. Agents do not reliably do that. Put the six required
field names and a skeleton example **inline in `scout.md`**, and treat
`--render-scout` plus schema validation as the belt-and-braces layer. Consider
a severity bump — at the policy-assigned tier this is a broken input contract,
not a formatting nit.

## FIXME-2 — Scouts do not honor "Return ONLY the ScopeProfile JSON"
`self-scan`, `severity:low`, `evidence:tool-confirmed`, `panel:architecture`

`agents/scout.md` ends with "Return ONLY the ScopeProfile JSON. No prose."
4 of 10 scouts (`._2 ._5 ._7 ._8`) returned analysis prose wrapped around the
JSON; `._5` returned the whole profile twice (fenced, then raw). Tolerant
parsing absorbs it, so it never surfaces — but the contract is not being met
and no test measures compliance.

## FIXME-3 — A scout violated its own template's spawn rule
`self-scan`, `severity:low`, `evidence:tool-confirmed`, `panel:architecture`

`scout.md`: "Set `spawn: true` when the group has ≥5 files or `risk` is
`high`." Group `._3` has 14 files and returned `spawn: false` for every lens.
Honored as returned rather than silently corrected — but it means the docs

## FIXME-4 — No agent-side fixture exclusion
`self-scan`, `severity:medium`, `evidence:tool-confirmed`, `panel:architecture`

`--tools-exclude` keeps deliberately-vulnerable fixtures out of *tool* ingest
(35 findings excluded in run 2). There is no equivalent for the agent path:
nothing stops discovery, scout, and fan-out from reviewing
`tests/fixtures/vulnerable-rust` as if it were production code — which run 1's
scout did, rating it high-risk. Run 2 excluded group `._9` **by hand**, which
is not a mechanism.

**Fix:** one exclusion setting that both `orchestrator.py` discovery and
`ingest_tools` honor, so a fixture corpus is excluded once, for both paths.

## FIXME-5 — Fan-out is bounded by orchestrator context, not agent capacity
`self-scan`, `severity:high`, `evidence:tool-confirmed`, `panel:architecture`

Every reviewer is read-only (PR #26), so every finding must transit the
orchestrator's context to reach disk. Measured in run 2: **one group of 11
reviewers cost ~55k tokens of orchestrator context** (~40k returned + ~15k
re-emitted to write 11 findings files). The remaining 63 planned reviewers
would have cost ~300k. Run 2 therefore covered 1 of 10 groups.

A workaround was proven in the same run: the verify phase dispatched 52
advisors through 4 general-purpose **sub-orchestrators**, each holding Write
and persisting verdicts itself. All 52 verdicts landed; the orchestrator's
context cost was four short tallies. Advisors stayed enforced read-only
shells — only the persistence layer changed.

**Fix to design:** a first-class `group_runner` role — an orchestrator-class
agent, not a reviewer — that owns fan-out for one group and writes that
group's findings files. See FIXME-6 for the write-scoping that should come
with it.

## FIXME-6 — A writing sub-orchestrator has an unscoped write surface
`self-scan`, `severity:medium`, `evidence:unverified`, `panel:security`

The sub-orchestrator pattern in FIXME-5 requires an agent with `Write`. Claude
Code's agent frontmatter grants a *tool*, not a *path* — `Write` means write
anywhere. That agent is in the trust path for findings persistence with no
mechanical bound on what it can touch.

Partial mitigations already in place: reviewers themselves stay read-only;
`AGENT_FORBIDDEN_FIELDS` strips `source`/`reinforced` at load, so a
sub-orchestrator cannot forge `tool_confirmed`; the post-fan-out clean-tree
check catches writes outside `.panopticon/`.

**Fix (proposed):** pre-assign the write surface and enforce it out of band —
a `PreToolUse` hook matching `Write|Edit|NotebookEdit` that denies any
`file_path` outside the allowlist derived from the dispatch plan's `out_file`
values. Enforcement then lives in the harness, not in prompt text. Consider a
third `meta.tool_policy_mode` value (`enforced+scoped-write`) so an artifact
records which posture actually applied.

## FIXME-7 — Group names are still `._N`
`self-scan`, `severity:low`, `evidence:tool-confirmed`, `panel:architecture`, `cosmetic`

Repo-scan groups are named `._1 … ._11`, from `basename('.')` plus an index
(`orchestrator.py`: `"%s_%d" % (base, i + 1)`). Carried over from run 1. The
names appear in findings filenames, dispatch plans, prompt ids, and per-group
grades — all of which are read by humans.

Two consequences beyond cosmetics, both hit during the run-2 completion:

1. **The target's directory basename leaks into every artifact name.** Scanning
   a repo at `/srv/acme-billing` names groups `acme-billing_1…`, and those names
   propagate into `findings-*.json` filenames and the report. That is a path
   disclosure in any artifact shared outside the scanning host.
2. **`._N` makes every artifact a hidden dotfile.** On macOS/Linux, `ls` and
   most glob patterns skip `.panopticon/prompts/._1-code-panel_review.md`. A
   resuming operator sees an apparently *empty* prompts directory and can
   conclude the prompts were never rendered. This happened verbatim while
   resuming this run.

**Fix:** derive group names from a stable, non-path-derived token (index, or a
hash of the group's file set), and never let a generated name begin with `.`.

## FIXME-10 — Truncated fan-out starves the highest-value panels first
`self-scan`, `severity:high`, `evidence:tool-confirmed`, `panel:architecture`

Observed when run 2's fan-out hit a hard session-wide subagent cap partway
through. Sub-orchestrators dispatch a group's entries in manifest order — code,
then test, then security, then architecture — so a truncation cuts the tail of
every group simultaneously. Result: **security ended at 14% coverage (3 of 21
entries) while code reached 65%**, and the security panel was missing entirely
for six of seven groups reviewed.

Any interruption — cap, timeout, crash, budget — therefore biases a partial
scan toward "no security findings", which is the single most misleading way for
a security review to fail. Nothing in the artifact would have flagged it: the
report has no notion of planned-versus-executed entries.

**Fix, two parts:**
1. Dispatch in panel-priority order (security and architecture first), so a
   truncated run loses style findings rather than injection findings.
2. Record planned-vs-executed entry counts per panel in the report `meta`, and
   refuse to emit a grade or gate verdict when they diverge — the same
   tolerant-but-honest posture `meta.schema_errors` already takes.

## FIXME-11 — Reviewers read outside their assigned group
`self-scan`, `severity:medium`, `evidence:tool-confirmed`, `panel:architecture`

`agents/panel-review.md` opens with "Review the listed files through the
`{panel}` panel." Nothing in the template confines the reviewer *to* that list,
and reviewers have Grep and Glob over the whole repo. Three independent
sightings, two in-house and one external:

- `._1-security-lens_sweep-known_vulns` filed `KVULN-008` against
  `docs/superpowers/2026-08-04-run2-fixmes.md` — not in group `._1`'s file list.
- `._7-security-lens_sweep-known_vulns` reasoned over `tests/test_run_tools.py`,
  which belongs to group `._8`.
- The external calibration operator reported the same drift as cross-panel
  duplicates.

Consequences: duplicate findings at one locus attributed to several groups,
per-group grades computed from files the group does not own, and wasted tokens
re-reading the same file across groups.

**Fix, two parts:** (1) add an explicit scope fence to the reviewer templates —
the assigned list is the review surface; reading beyond it is allowed only to
*resolve* a claim about an in-scope file, and a finding must be *located* in
scope. (2) In `synthesize.py`, count findings whose `location.file` falls
outside the emitting group's file list and surface the count in `meta` —
advisory, not fatal, per the tolerant-by-design rule.

## FIXME-12 — A partially-failed fan-out has no resume path
`self-scan`, `severity:high`, `evidence:tool-confirmed`, `panel:architecture`

Every dispatch-plan entry already declares an `out_file`, so a completed entry
is *self-evident on disk* — but nothing reads that. A run interrupted by a
subagent cap, an API error, or a timeout has no supported way to continue, and
re-running dispatches everything from scratch.

This is not hypothetical. Run 2 stopped at 33 of 74 entries and was resumed only
by hand-diffing `prompt-manifest.json` against the findings files on disk. The
external operator independently lost 2 of 5 reviewers to API errors and asked
for the same capability.

**Fix:** a `--resume` mode that treats "out_file exists and parses as findings
JSON" as done and dispatches only the remainder. The same predicate works for
the verify phase, keyed on `.panopticon/verdicts/{queue_id}.json`. Log the skip
count so a resumed run never reads as a fresh full scan.

## FIXME-13 — Pass 1 and pass 2 build *different* verify queues
`self-scan`, `severity:high`, `evidence:tool-confirmed`, `panel:correctness`

Verdicts are keyed by `queue_id`, and `queue_id` is **positional**
(`NNN-FINDING-ID`, `evidence.build_verify_queue`). The two passes of a single
run do not compute the same positions:

- Pass 1 (`--emit-verify-queue`) builds the queue from
  `prepare_findings(...)` **alone**.
- Pass 2 (`build_report`) runs `aggregate_tool_findings(...)` **first**, then
  `prepare_findings(...)`, then builds the queue.

`aggregate_tool_findings` merges tool findings, changing the list's length and
order — so every position after the first merge shifts. In this run, 13 of 380
verdicts landed on ids pass 2 did not recognize; synthesize reported
`verdict file(s) for unknown queue_id(s)` and silently left those 13 findings
`unverified`.

**This is not cosmetic.** Re-filing the 13 by identity (finding id + file +
line) and re-running changed the report: a CRITICAL `eval()` finding against
`tests/fixtures/insecure-js/app.js` **disappeared**, because its advisor verdict
was a REJECTION that had been unreachable. Incomplete verdict coverage was
manufacturing a false CRITICAL against panopticon's own security posture. Full
coverage also moved the grade D → F, since the restored findings became
gate-eligible.

The `NNN-FINDING-ID` format limits the blast radius — a shifted entry usually
fails to match rather than matching the *wrong* finding — but that guard is not
sound here: this run emitted 55 duplicate-finding-id schema errors, and two
findings sharing an id at different positions can silently mis-map.

**Fix:** build the verify queue exactly once, from the same
aggregated-and-prepared list both passes use, and key verdicts by the finding
**fingerprint** rather than queue position. Same identity-instability class as
ARCH-103. Until then, a re-run of pass 1 invalidates every existing verdict —
the run-2 resume doc's assumption that "the queue will grow, not change" was
false, and all 52 prior verdicts had to be discarded.

## FIXME-14 — Sub-orchestrator dispatch has two repeatable failure modes
`self-scan`, `severity:medium`, `evidence:tool-confirmed`, `panel:architecture`

The FIXME-5 workaround (sub-orchestrators that hold `Write` and persist their
group's outputs) works, but running it at scale exposed two failure modes that
the eventual `group_runner` role must design against:

1. **Stalling.** Several sub-orchestrators ended their turn saying they would
   "await the background notification" before retrying. A subagent that stops is
   *finished* — nothing resumes it. Work sat unstarted until the parent noticed
   and re-sent instructions. The role's contract must state: never end a turn
   while dispatched work is unresolved.
2. **Re-dispatching instead of resuming.** On a mid-response API failure, the
   cheap recovery is to *resume* the existing agent (its context and partial
   work survive), not to dispatch a fresh one. Workers that resumed recovered
   full output; a re-dispatch pays for the whole run twice.

A third, milder issue: one sub-orchestrator reported byte counts for files it
had written that did **not** match disk (16279 reported vs 23521 actual, all
five entries wrong). Its artifacts were sound — the numbers were recalled rather
than measured. Status reporting must come from tool output, never recollection,
or an orchestration report becomes a second unverified claim surface.

**Efficiency note for the same role:** verifying one claim per advisor is the
expensive shape. Grouping 2–3 queue entries that share a target file into one
advisor run cut this run's verify phase from 380 dispatches to 123, with each
advisor reading the shared file once. Returning verdicts in delimited
`===VERDICT <queue_id>=== … ===END===` blocks keeps persistence a pure
transcription step (no parse-and-re-serialize in the trust path); across 123
batches this produced **zero** finding-id mismatches.
