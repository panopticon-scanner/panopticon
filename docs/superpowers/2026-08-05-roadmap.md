# Panopticon roadmap — from remediation to daily driver

**Written:** 2026-08-05, after P1 and P2 shipped.
**Status of record:** 390 open issues, 33 closed. Milestone *Remediation 1*: 34 open, 4 closed.

## Where we are

Two packages have shipped. **P1** (adapter-execution containment) put every scan
container behind `--network none` with advisory data baked in, contained
roslyn-secguard rather than preventing it, and demonstrated containment with a
committed hostile-csproj probe. **P2** (run integrity and gate trust) made
verify-queue identity content-addressed, made both passes build the queue from
one pipeline, inverted evidence precedence so an advisor can refute a scanner,
and added `meta.tool_axis` / `meta.verdicts`.

A verification session on 2026-08-05 then found that the tool layer had been
partly broken in ways nothing reported:

- **dependency-check had never produced a finding from a container.** Its data
  directory was `chmod a+rX`; H2 blocks rather than failing when it cannot lock,
  so every scan burned a 900s timeout and returned nothing (#451, fixed).
- **semgrep spent ~96s per invocation** on a version check that `--metrics=off`
  does not cover, blocking against `--network none` (fixed: 2m10s → 35s).
- **Nothing ever executed the image.** Both regressions passed CI, because the
  publish workflow builds and pushes without running a single tool (#455, fixed
  by a build-time gate).
- **The published image is amd64-only**, so it cannot be pulled on Apple
  Silicon or ARM runners — which meant a stale local build silently stood in for
  it, and that stale image is what produced a wrong bug report (#461, open).

That episode is the reason this roadmap is ordered the way it is.

## The organizing principle

Three questions, in order. Everything else is quality work behind them.

1. **Does the scanner tell the truth about what it did?** A report that cannot
   distinguish "we did not look" from "we looked and found nothing" is worse
   than no report, because it is trusted.
2. **Does it actually cover the repo?** Run 2 reviewed 1 of 10 groups.
3. **Is it usable daily?** Full scans are calibration; PR review is the habit.

Instrumentation honesty comes first because every later phase's evidence depends
on it — including our own ability to tell whether a phase worked.

## Phase 1 — Honest instrumentation

**Issues:** #456, #457, plus the P2 follow-ups filed in Phase 0.

This is the general form of what bit us. #456: an adapter that writes an empty
or unparseable file still counts as having run, which is what let a dead semgrep
look healthy — and it weakens P2's own `meta.build_executing_tools`, since
`tools_ran` is derived from filenames present. #457: a scout can decline the
tool layer silently, and `tool_policy_mode` falls through to `"advisory"` when
it cannot find the dispatch plan, so a fully enforced run under-reports itself.

**Exit:** no run can look more complete than it was. Concretely — a failed
adapter is loud; a skipped tool layer appears in `meta` and the terminal
summary; a capped verify queue is visible in the artifact, not just in stderr;
the HTML report states verification coverage next to the grade.

**Why first:** pure Python, no image rebuild, and it is the common cause behind
both silent failures found on 2026-08-05.

## Phase 2 — Fan-out architecture (P3)

**Issues:** #435 (group_runner), #442 (resume), #440 (truncated fan-out starves
the highest-value panels), #436 (unscoped write surface), #444 (sub-orchestrator
dispatch failure modes), #146 (clean-tree check exempts the compromise
directory), #275 (enforcement degrades to advisory).

The flagship's central limitation: fan-out is bounded by orchestrator context
rather than agent capacity, so a whole-repo scan silently reviews a fraction of
the repo and the truncation takes the *highest-priority* panels first.

**#444 is unusually well evidenced.** The two failure modes it documents —
a sub-orchestrator that stalls awaiting a notification, and re-dispatching
instead of resuming — were both reproduced by this project's own subagent
dispatches during P1/P2 execution. The workaround (never end a turn with work
unresolved; background long operations and short-poll) is recorded in the
session lessons and should become the contract `group_runner` enforces.

**Exit:** a whole-repo scan covers every group, survives a partial failure via
resume, and records in `meta` which panels were cut and why.

## Phase 3 — PR-first review mode (#449)

Depends on P2's fingerprint-keyed identity (shipped) and is materially better
after Phase 2, because delta mode subtracts against a full-scan baseline —
coverage in the baseline is precision in the delta.

**Exit:** `--pr N` produces findings new relative to the latest full-scan
artifact, gates on new fingerprints only, with the verify phase mandatory (run
2's 27% advisor rejection rate is the argument).

## The 350-issue tail — a decision, not a phase

350 open issues are run-2 findings at MEDIUM/LOW/INFO that the triage arc never
reached (it dispositioned the 15 FIXMEs, 5 CRITICALs and 52 HIGHs). They dwarf
the rest of the backlog and will distort any velocity signal.

**Recommendation: let run 3 arbitrate, after Phase 2.** P2 gave findings stable,
content-addressed fingerprints, so a re-scan on the fixed pipeline can be
diffed against the existing set rather than hand-triaged. Findings that recur
are re-filed with matching identity; findings that do not recur were either
fixed, false, or unreachable — and can be closed as a cohort with that stated
rationale. This converts 350 hand-triage decisions into one scan plus a diff.

The alternative — a second triage arc with `scripts/triage.py` — is available
and proven, but spends days of judgment on findings whose provenance we now know
was incomplete: run 2 ran without semgrep, and its tool axis was never verified.

**Do not close the tail before run 3.** Their fingerprints are the input to the
diff.

## Definition of done

1. Milestone *Remediation 1* closed.
2. A **run-3 self-scan** on the fixed pipeline — full group coverage, verify
   phase, honest instrumentation — grading better than run 2's F, with the tail
   reconciled against it.
3. **PR mode in daily use**: `--pr N` on real pull requests, gating on new
   fingerprints, fast enough to sit in CI.

Phases 0 and 1 are prerequisites for trusting anything after them. Phases 2 and
3 are the product. Phases 4–7 are the quality bar that keeps it honest.
